---
title: Warm handoff
description: Hold a caller, introduce a second agent privately, then leave the caller and second agent connected.
---

A warm handoff transfers a live caller from one agent to another without dropping them: the first agent puts the caller on hold, briefs the next agent privately, then disconnects while the caller and next agent keep talking.

In this pattern, all three parties are dialed into one conference: the caller (A), the first agent (B), and the next agent (C). Each participant is an ordinary call, so you read, end, and price it with `GET /calls/{call_id}` and `PATCH /calls/{call_id}` like any other.

## Before you start

- **Check conference pricing in `GET /prices`:** look for `call.conference.participant`. Each participant is billed for their time in the conference on top of each call leg's price. If your account has no price for conference participants, inviting one answers `403 forbidden` with `error.details.reason` set to `conference_pricing_missing`, and nothing is dialed or charged. Contact Sendblue to have a rate set.
- **Funds for three calls:** the longest possible call and conference visit are held from your balance when each participant is accepted, and settled when that leg ends.
- **Credentials:** an API key or the account token as `Authorization: Bearer`, like every other route. Inviting a participant needs `calls:create`; holding, ending, and removing need `calls:write`; reads need `calls:read`.

```bash
API="https://omni-api.sendblue.com"
AUTH="Authorization: Bearer $SENDBLUE_KEY_ID.$SENDBLUE_KEY_SECRET"
ROOM="support-4821"   # any name unique to this conversation, 1 to 128 characters
```

## Run the handoff

<Steps>
  <Step title="Bring the caller and first agent together">
    Invite the caller. The first invitation to a name starts the conference:

    ```bash
    curl "$API/conferences/$ROOM/participants" \
      -H "$AUTH" \
      -H "Idempotency-Key: support-4821-caller" \
      -H "Content-Type: application/json" \
      -d '{
        "from": "+14155550100",
        "to": "+14155550101",
        "label": "caller",
        "start_conference_on_enter": true,
        "end_conference_on_exit": false,
        "beep": "never",
        "status_callback": "https://example.com/voice/events",
        "status_callback_events": ["initiated", "ringing", "answered", "completed"],
        "conference_status_callback": "https://example.com/voice/events",
        "conference_status_callback_events": ["start", "end", "join", "leave", "hold"]
      }'
    ```

    The `201` response is the participant. Save its `call_id` (`CA…`) and `conference_id` (`CF…`):

    ```json
    {
      "call_id": "CA0123456789abcdef0123456789abcdef",
      "conference_id": "CF0123456789abcdef0123456789abcdef",
      "label": "caller",
      "status": "queued",
      "muted": false,
      "hold": false,
      "coaching": false,
      "call_id_to_coach": null,
      "start_conference_on_enter": true,
      "end_conference_on_exit": false,
      "queue_time_ms": 0,
      "created_at": "2026-11-24T18:00:00.000000Z",
      "updated_at": "2026-11-24T18:00:00.000000Z"
    }
    ```

    Repeat the request with the first agent's phone number, `"label": "agent"`, and a new `Idempotency-Key`. From here on you can address the conference by its ID. Wait until both have joined, either from the `join` callback events or by listing participants until each has `"status": "connected"`:

    ```bash
    curl "$API/conferences/$CONFERENCE_ID/participants" -H "$AUTH"
    ```

    Setting `end_conference_on_exit` to `false` on every participant ensures the first agent can leave later without ending the conference for everyone else.

    <Note>
      Repeating an invitation with the same `Idempotency-Key` returns the same participant and dials nobody twice. A key that was used for another conference or another body answers `409 idempotency_conflict`.
    </Note>
  </Step>

  <Step title="Hold the caller and bring in the next agent">
    Place the caller on hold. The participant is named by its call ID or its label:

    ```bash
    curl -X PATCH "$API/conferences/$CONFERENCE_ID/participants/$CALLER_CALL_ID" \
      -H "$AUTH" \
      -H "Content-Type: application/json" \
      -d '{"hold": true}'
    ```

    The change takes effect asynchronously: the `200` response is the participant as it was when the change was recorded. Confirm the hold from the `hold` event, or read the participant until `hold` is `true`:

    ```bash
    curl "$API/conferences/$CONFERENCE_ID/participants/$CALLER_CALL_ID" -H "$AUTH"
    ```

    Then invite the next agent into the same conference (the same request as step 1, with their phone number, `"label": "next-agent"`, and a new `Idempotency-Key`). Wait for them to join before starting the briefing. The caller hears none of it.
  </Step>

  <Step title="Reconnect the caller and release the first agent">
    Take the caller off hold, confirm `hold` is `false`, and then end the first agent's call:

    ```bash
    # Take the caller off hold
    curl -X PATCH "$API/conferences/$CONFERENCE_ID/participants/$CALLER_CALL_ID" \
      -H "$AUTH" \
      -H "Content-Type: application/json" \
      -d '{"hold": false}'

    # End the first agent's call
    curl -X PATCH "$API/calls/$AGENT_CALL_ID" \
      -H "$AUTH" \
      -H "Content-Type: application/json" \
      -d '{"status": "completed"}'
    ```

    The caller and the next agent stay connected in the same conference on their original call legs.

    <Tip>
      To cancel a handoff before completing it, take the caller off hold and end the **next agent's** call instead.
    </Tip>
  </Step>

  <Step title="End the conference">
    The conversation ends when the remaining callers hang up. To end it yourself, end the conference, which ends every participant's visit:

    ```bash
    curl -X PATCH "$API/conferences/$CONFERENCE_ID" \
      -H "$AUTH" \
      -H "Content-Type: application/json" \
      -d '{"status": "completed"}'
    ```

    A name that is used again after its conference ended starts a new conference with a new ID.
  </Step>
</Steps>

## Callback events

`status_callback` and `conference_status_callback` are per-request URLs. The requests Omni sends to them are form-encoded with Twilio's parameter names and signed with `X-Twilio-Signature`, not the signed JSON described in [Webhooks](/webhooks):

- **Call leg events** (`status_callback`): `initiated`, `ringing`, `answered`, `completed`
- **Conference events** (`conference_status_callback`): conference `start` and `end`, plus per-participant `join`, `leave`, and `hold` changes

Drive each handoff transition from these events rather than fixed delays.

## Pricing

Each of the three legs is billed as an outbound call, plus each participant's conference time at your `call.conference.participant` rate. Read each leg's settled `price` via `GET /calls/{call_id}`, and inspect full ledger entries in `GET /admin/billing/transactions`.
